이 페이지는 pandas
개발의 주요 주제들에 대한 개요를 제공합니다. 각 항목은 구현하는 데 비교적 많은
노력이 필요합니다. 전담 자금이나 기여자의 관심이 있으면
더 빠르게 달성될 수 있습니다.

뜻은 아닙니다. 로드맵은 프로젝트에 대한 더 크고
근본적인 변경, 개발자의 시간으로 수개월에서 수년이 걸릴 만한 작업을
위한 것입니다. 범위가 더 작은 항목들은 계속해서
[이슈 트래커](https://github.com/pandas-dev/pandas/issues)에서 추적됩니다.

PDEP에 대한 자세한 정보와 제출 방법은

### 확장성

pandas의 `extending.extension-types`는
NumPy 자료형을 사용자 정의 자료형과 배열 저장 방식으로 확장할 수 있게 해 줍니다.
pandas는 내부적으로 확장 자료형을 사용하며, 외부 라이브러리가
자체 사용자 정의 자료형을 정의할 수 있도록 인터페이스를 제공합니다.

pandas의 여러 부분은 여전히 의도치 않게 데이터를 NumPy
배열로 변환합니다. 이러한 문제는 중첩된 데이터에서 특히 두드러집니다.

라이브러리 전반에 걸쳐 확장 배열 처리를 개선하여,
NumPy 배열 처리와 동작이 더 일관되도록 만들고 싶습니다. pandas 내부를 정리하고
확장 배열 인터페이스에 새 메서드를 추가하는 방식으로 이를 진행할 예정입니다.

### 문자열 자료형

현재 pandas는 텍스트 데이터를 `object` 데이터형의 NumPy 배열에 저장합니다.
현재 구현에는 두 가지 주요 단점이 있습니다. 첫째, `object`
데이터형은 문자열에 한정되지 않습니다. 어떤 파이썬 객체라도 `object` 데이터형 배열에
저장할 수 있고, 문자열만 저장하는 것이 아닙니다. 둘째, 효율적이지 않습니다.
NumPy의 메모리 모델은 가변 폭의
텍스트 데이터에 특별히 잘 맞지 않습니다.

첫 번째 문제를 해결하기 위해, 문자열 데이터를 위한 새 확장 자료형을
제안합니다. 초기에는 옵트인 방식으로, 사용자가 명시적으로
`dtype="string"`을 요청하도록 할 예정입니다. 이 문자열 데이터형을 뒷받침하는 배열은 초기에는
현재 구현과 같이, 파이썬 문자열로 이루어진 `object` 데이터형의 NumPy 배열이
될 수 있습니다.

두 번째 문제(성능)를 해결하기 위해서는, 대안적인
메모리 내 배열 라이브러리(예: Apache Arrow)를 탐색할 예정입니다. 작업의 일환으로
pandas 사용자가 기대하는 특정 연산(예: `Series.str.upper`에서 사용되는 알고리즘)을
구현해야 할 수도 있습니다. 해당 작업은
pandas 외부에서 진행될 수도 있습니다.

### Apache Arrow 상호 운용성

[Apache Arrow](https://arrow.apache.org)는 메모리 내 데이터를 위한
언어 간 개발 플랫폼입니다. Arrow의 논리적 자료형은
일반적인 pandas 사용 사례와 밀접하게 정렬되어 있습니다.

pandas 내에서 Arrow 메모리와
자료형에 대한 더 잘 통합된 지원을 제공하고자 합니다. 이를 통해 Arrow의 I/O
기능을 활용하고, Arrow를 사용하는 다른 언어 및 라이브러리와의
상호 운용성을 더 개선할 수 있습니다.

### 인덱싱과 내부 구조의 분리

pandas 자료 구조에서 값을 가져오고 설정하는 코드는
리팩터링이 필요합니다. 특히, 키(예: `DataFrame.loc`의 인자)를 위치로
변환하는 코드와, 그 위치를 사용해 값을 가져오거나 설정하는
코드를 명확히 분리해야 합니다. 이는
제안된 BlockManager 재작성과 관련이 있습니다. 현재 BlockManager는 위치 기반이 아닌
라벨 기반 인덱싱을 사용하는 경우가 있습니다. BlockManager는
오직 위치 기반 인덱싱만 다루도록 하고, 키를 위치로 변환하는 작업은
전적으로 더 상위 계층에서 처리하도록 제안합니다.

인덱싱은 미묘한 부분이 많은 복잡한 API입니다. 이 리팩터링에는 신중함과
주의가 필요합니다. 다음 원칙들이 인덱싱 코드 리팩터링의 길잡이가 되어,
더 깔끔하고 단순하며 성능이 좋은 코드로 이어져야 합니다.

1. 라벨 인덱싱은 같은 라벨에 대해 한 축을 두 번 들여다보아서는 안 됩니다.
   이는 어떤 검증 단계든 다음 중 하나여야 함을 의미합니다:

- 검증을 일반적인 특성(예: 키/인덱스의 데이터형/구조)에 한정하거나,
- 실제 인덱싱에 결과를 재사용해야 합니다.

2. 인덱서는 다른 인덱서를 명시적으로 호출하는 데 의존해서는 안 됩니다.
   예를 들어, `.loc`의 어떤 내부 메서드가
   `__getitem__`의 어떤 내부 메서드(또는 공통 기반 클래스의 메서드)를 호출하는 것은 괜찮지만,
   `.loc`의 코드 흐름에서 `the_obj[something]`가 나타나서는 안 됩니다.

3. 위치 기반 인덱싱의 실행은 라벨을 절대 사용해서는 안 됩니다 (현재는 안타깝게도 그런 경우가 있습니다).
   즉, `.iloc`에 대한 getter 호출 (또는 우변이 인덱스가 아닌 setter 호출)의
   코드 흐름은 어떤 식으로든 객체의 축을 사용해서는 안 됩니다.

4. 인덱싱은 값에 접근하거나 수정하는 작업(즉, `._data` 또는 `.values`에 작용하는 작업)을 한 번 이상 해서는 안 됩니다.
   따라서 다음 단계들은 명확히 분리되어야 합니다:

- 각 축에서 접근/수정할 위치를 찾습니다
- (접근하는 경우) 반환할 객체의 자료형(차원 수)을 결정합니다
- 실제로 값에 접근/수정합니다
- (접근하는 경우) 반환 객체를 구성합니다

5. 4.i와 4.iii의 분리에 대한 따름 원칙으로, 데이터가 어떻게 저장되는지를 다루는 모든 코드는
   (여러 데이터형 처리, 희소 저장 방식, 카테고리형, 외부 자료형의 어떠한 조합도 포함하여)
   영향을 받는 행/열을 식별하는 코드로부터 독립적이어야 하며,
   오직 4.i 단계 이후에만 수행되어야 합니다.

- 특히, 이러한 코드는 `pandas/core/indexing.py`에 위치하지 않는 편이 좋습니다
- ... 그리고 축의 자료형에 어떤 식으로든 의존해서는 안 됩니다 (예: `MultiIndex`에 대한 특수 처리 금지)

6. 1.i의 따름 원칙으로, `Index` (하위) 클래스는 라벨의 유효성 검증(실제 조회를 동반하지 않는)을 위한 메서드와,
   라벨의 변환/조정/조회가 필요한 작업을 위한 메서드를 각각 분리하여 제공해야 합니다.

7. 시행착오 방식의 사용은 제한되어야 하고, 실제로 예상되는 예외만
   (보통 `KeyError`) 잡도록 한정되어야 합니다.

- 특히, `try... exception`의 `except` 부분에서 (의도적으로) 새 예외를 발생시키는 일은 없어야 합니다 exception\`

8. setter와 getter에 특정되지 않은 코드 부분은 공유되어야 하며,
   동작에 작은 차이가 예상될 경우 (예: `.loc`로 가져올 때는 누락된 라벨에 대해 예외를 발생시키지만,
   설정할 때는 그렇지 않음) 별도의 매개변수로 관리할 수 있습니다.

### Numba 가속 연산

[Numba](https://numba.pydata.org)는 파이썬 코드를 위한 JIT 컴파일러입니다.
pandas가 사용자 정의 함수를 받아들이는 곳(예:
`Series.apply`,
`DataFrame.apply`,
`DataFrame.applymap`, 그리고 groupby와 윈도우
컨텍스트)에서 사용자가 직접 Numba로 JIT 컴파일한 함수를 적용할 수 있는
방법을 제공하고자 합니다. 이를 통해 위 연산에서
사용자 정의 함수의 성능이 컴파일된 코드 내에서 유지되어
향상될 것입니다.

개선하고자 합니다. 구체적인 목표는 다음과 같습니다

  개선하여, 탐색과 콘텐츠 찾기를 더 쉽게
  하기.

### 성능 모니터링

pandas는 성능 퇴행을 모니터링하기 위해
[airspeed velocity](https://asv.readthedocs.io/en/stable/)를 사용합니다. ASV 자체는 훌륭한 도구이지만,
오픈 소스 프로젝트의 작업 흐름에 통합하려면 추가 작업이 필요합니다.

현재 pandas 메인테이너들로 구성된 [asv-runner](https://github.com/asv-runner) 조직은
ASV 위에 만들어진 도구를 제공합니다. 여러 프로젝트의
벤치마크를 실행하는 물리 머신과, 벤치마크 실행 및 결과 보고를 관리하는
도구들을 보유하고 있습니다.

이러한 도구의 개선과 유지보수에 대한 자금 지원을 받고자 하는 점은 다음과 같습니다

- 더 안정적으로 만들기. 현재는 메인테이너가 시간이 날 때
  밤과 주말에 유지보수되고 있습니다.
- <https://pyperf.readthedocs.io/en/latest/system.html>를 참고하여
  안정성 향상을 위해 벤치마크용 시스템 튜닝하기
- PR이 병합되기 _전에_ ASV 실행을 요청하는 GitHub 봇 구축하기.
  현재 벤치마크는 매일 밤에만 실행됩니다.
